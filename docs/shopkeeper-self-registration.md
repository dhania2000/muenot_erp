# Shopkeeper self-registration and mobile Meta onboarding

The pending application is **not** a tenant or ERP user. `shopkeeper_applications` stores an existing bcrypt password hash, normalized contact details, consent timestamps and a SHA-256 hash of a 256-bit registration receipt. The receipt is returned once, must be kept in secure mobile storage, and allows status polling only. Pending and rejected applicants have no mobile session and cannot call business APIs. `shopkeeper_application_events` records transitions. Existing manual Shopkeeper creation is unchanged.

Super Admin approval locks the application row and writes the existing `tenants`, `shopkeeper_profiles`, `users` and `tenant_subscriptions` records using the shared provisioning writer in a single MySQL transaction. Tenant type and owner role are server-selected; the selected active Shopkeeper plan supplies entitlements. The same original bcrypt hash is copied to the owner record, so the existing `/api/mobile/v1/auth/login` works after approval. Rejection keeps the application; a Super Admin may reopen it. Tenant suspension uses the existing status gate, which invalidates mobile business access server-side. Registration receipt polling returns only customer-facing fields.

## Mobile app handoff

1. `POST /api/mobile/v1/auth/register` with business/owner details, password, `termsAccepted: true` and `privacyAccepted: true`. Store `registrationToken` securely. Do not send tenant, role or plan fields.
2. `GET /api/mobile/v1/auth/registration-status` with `Authorization: Registration <registrationToken>`. Poll while `PENDING_APPROVAL`. Show the safe `rejectionReason` if rejected. On `APPROVED`, use the **same email/password** with the existing `POST /api/mobile/v1/auth/login` and existing refresh lifecycle.
3. After login, an approved Shopkeeper owner/admin calls `POST /api/mobile/v1/whatsapp/onboarding-session` with the mobile bearer token. Open its `url` in Chrome Custom Tabs/external browser. The opaque 10-minute launch token is a URL **fragment**; it is not sent to the web server in the request URL and is removed from browser history after load.
4. The Muenot-hosted page launches the existing Meta JS SDK Embedded Signup. The existing server-side signup service binds a one-time state to the tenant/user, exchanges Meta's code, encrypts and saves credentials, subscribes the webhook and performs Cloud API phone registration. The Android app never receives Meta credentials or the authorization code.
5. Browser returns to `muenot://whatsapp/connected` or `muenot://whatsapp/error`, with **no query parameters**. On either return, call authenticated `GET /api/mobile/v1/whatsapp/status`; treat only `CONNECTED` as messaging-ready. `CONNECTING` and `ACTION_REQUIRED` require follow-up/retry. Reconnect starts a new session.

Admin routes: `GET /api/platform/shopkeepers/applications`, `GET /api/platform/shopkeepers/applications/{id}` (platform staff); `POST /api/platform/shopkeepers/applications/{id}` with `{action:"approve",planCode,startTrial}`, `{action:"reject",reason}`, or `{action:"reopen"}` (Super Admin). The `/platform/shopkeepers` page shows pending/approved/rejected/suspended filters and the existing manual tenant directory.

Schema migrations: `2026-09-23-shopkeeper-self-registration.sql`, `2026-09-23-mobile-whatsapp-onboarding.sql`. Existing tenant/user/profile/subscription, mobile auth, WhatsApp integration, registration and notification schemas remain authoritative.

Deployment requirements: production `APP_URL` or `NEXT_PUBLIC_APP_URL` must be HTTPS and match Meta's allowed JS SDK domain; existing Meta App ID, Embedded Signup Config ID, App Secret and encryption configuration must be present server-side. Apply migrations before traffic (runtime schema ensure is also additive). Test with a real Meta test business and a real MySQL instance before enabling in production.

Current limitations: rejected pending applicants cannot receive FCM/in-app notifications because they do not yet have a user/device; they see the rejection through the secure status endpoint. Self-registered email is **not** falsely marked verified; if `security.require_email_verification` is enabled, the existing email-verification step must be completed before mobile login. A distributed rate limiter/CAPTCHA should replace the existing in-memory limiter for multi-node deployments. A true end-to-end Meta handshake requires live Meta configuration and cannot be proved by unit tests alone.
